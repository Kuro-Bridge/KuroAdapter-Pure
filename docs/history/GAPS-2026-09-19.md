## 2. 四条核心缺口裁决（详）

### 2.1 G1a status 快照 quit 计数偏大 ——【修】

- **登记原文**：「leave 时推送的 status 快照仍计入离开玩家（23:50:55 与 00:03:18 leave 后
  `onlinePlayers:1`，实际 0 人）——quit 处理顺序导致计数偏大」（SMOKE-2 §6-3）。
- **根因定位**：`paper/.../ConnectionListener.java` `onQuit` 在 `PlayerQuitEvent` 窗口内
  现取 `Bukkit.getOnlinePlayers().size()`——Paper 该事件触发时**退出者尚未移出在线列表**
  （SMOKE-2 真机两例实证）。:36 注释「进出服后的状态快照（在线数已变化…）」对 join 成立
  （事件时新玩家已入列）、对 quit 不成立——实现与自身注释相悖，非有意边界。
- **主仓语义**：主仓不自维护计数器，join/quit 事件后现取（主仓 `ConnectionListener`
  + MVP1-NOTES M-04「在线数恰好变化」）；主仓同样假设 quit 时取到新值——Pure 真机暴露
  该假设在 Paper 1.21.4 上对 quit 不成立（两仓共同的登记级发现，Pure 先修）。
- **方案**：保持「事件后现取」语义，只修 quit 窗口口径——按 UUID 剔除退出者后计数；
  退出者已不在列表（被先行移除/未来语义变化）则不重复剔除，双向稳健。口径纯函数
  `StatusCounts.countExcluding` 落 `:core/server`（:paper 无测试设施且 Bukkit 事件链
  不可单测；:paper 侧只留 2 行接线）。
- **验证**：`:core` 新增 `StatusCountsTest` ×4（99 → 103，`--no-build-cache` 全绿）；
  真机复验顺延（§5）。

### 2.2 G1b `query status` 缓存时效 ——【不修·文档化】

- **登记原文**：「`query status` 返回该缓存，事件驱动场景下可长期滞后（23:54:08 查询
  返回 3 分钟前快照）…协议文本允许，但与 leave 计数偏大叠加会放大失真」（SMOKE-2 §6-3）。
- **主仓语义**：明文接受——`latestStatus` 仅在 status 事件帧（= 玩家进出服时刻）更新，
  无 TTL 无主动刷新；query 本地作答是零 IPC 设计点（主仓 design.md / M-04），周期兜底
  已被 ADR-034 结论 5 裁决**不实施**。
- **裁决**：对齐主仓，维持缓存最近一帧语义；协议文本允许。G1a 修复后「放大失真」的
  源头已除，滞后窗口回到诚实语义（值 = 最近一帧真实快照，仅可能滞后）。文档化落点：
  STATUS 该条目改写为「已修计数 + 接受滞后」两段；SMOKE-2 §6-3 勾账标注。

### 2.3 G2 `version` 命令只捕获同步首行 ——【不修·文档化】

- **登记原文**：「`{"ok":true,"output":["Checking version, please wait..."]}`；异步版本
  详情…随后直落控制台，不在 command_result 内。属收集窗口设计边界（主仓同构），登记供
  协议文档明示」（SMOKE-2 §6-4）。
- **主仓语义**：主仓 command 语义 = 输出行全量聚合（`NodeIpcTest` 断言多行 output），
  无「sync 行」概念；但 version 的异步余量在主仓同款收集窗口（同步窗口 + Server thread
  过滤，G15）下同样不可得——「窗口内全量、窗口外不收」即两仓一致的命令收集边界，
  version 是其在 Bukkit 内建命令上的显形。
- **裁决**：不修。扩展窗口需「异步完成」时长启发式，破坏同步窗口设计并引入不确定延迟；
  主仓同构，协议行为一致性优先。登记原话的待办「供协议文档明示」即文档化动作：
  STATUS / README 措辞已在且保留，SMOKE-2 §6-4 勾账标注指向本册。

### 2.4 G3 控制台 `say` 不转发 ——【不修·显式裁决为非目标】

- **登记原文**：「非玩家聊天源不转发：控制台 `say` 无帧（ChatListener 仅
  AsyncChatEvent）。协议未承诺；登记为已知边界」（SMOKE-2 §6-5）——**裁决悬置属实**，
  两处登记均无裁决语句。
- **裁决：控制台（及一切非玩家源）聊天显式不进转发链，定为非目标**。理由：
  1. **对齐主仓**：主仓 chat 转发链唯一入口即 `AsyncChatEvent`（玩家聊天 + 权限门），
     无任何日志→chat 通道——主仓语义为「隐式排除」，Pure 不扩大；
  2. **协议未承诺**：`game_chat` body 以玩家名承载主体，控制台广播无玩家语义
     （SMOKE-2 §6-5 原话），转发即协议外扩形；
  3. **回环/噪音**：管理广播（say/announce）进 IM 转发链会全频道放大并可能与
     平台→游戏广播成环。
- **配套**：主仓存在显式通道先例 `/kurobridge send`（控制台可显式发一条 chat）——
  Pure 未实装，**登记为未来增强（非缺口、非本线动作，无发版不加功能）**；若未来实装，
  控制台进链走显式命令、与「say 不转发」裁决不冲突。
- **落点**：STATUS 措辞从「协议未承诺」升级为「显式非目标（裁决见本册 §2.4）」；
  `ChatListener` javadoc 补显式排除注记（docs↔code 联动）。
